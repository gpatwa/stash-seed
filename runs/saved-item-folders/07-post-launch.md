## What we'd do differently

- **Check `MODEL_ROUTING.md` before spawning, not after.** `STATE.md`'s Trace table shows Scope Review ran on **opus** at medium effort. Per `MODEL_ROUTING.md` Layer 1, Engineering Manager falls under "everyone else" → sonnet default, and Tier 2 uses the static defaults with no escalation (Layer 2). This is an unprincipled divergence — not a deliberate escalation-on-failure (Layer 3, which would need a prior failed attempt) and not noted anywhere in `STATE.md`, even though the protocol's own "Recording" section requires a written reason when actual routing diverges ("silent divergence is how routing policies rot"). No harm resulted here — Scope Review's output was solid — but the point of routing policy is that it's checked *before* the spend, not rationalized after the fact if someone happens to look. Concrete fix: the Orchestrator should read `MODEL_ROUTING.md`'s role table immediately before every spawn call, not rely on memory of the defaults.
- **QA's cross-user probe should include the third-order enforcement point, not just the two most obvious ones.** QA mutation-tested `assignItemToFolder` and `deleteFolder` (the two functions a caller actually invokes) but never called `clearFolderFromItems` directly with a folderId collision — the exact scenario SEC-1 needed. When a spec names N enforcement points (the Architect's table had 6 rows), QA's probe should exercise all N directly, not just the ones reachable through the "normal" call path.
- **A permanent test named after an invariant should assert that invariant's specific failure mode, not a nearby one.** SEC-2 existed because `invariant 4 — no content in audit` asserted item-content absence and a `name`-key absence, but never grepped for the actual folder-name *string*. The leak was only caught incidentally by an unrelated deep-equal shape test — a guard that legitimately changes shape the next time a field is added. Write the assertion that matches the test's own name, not an adjacent one that happens to also catch the case today.

## Carry-forward to next PRD in this area

- **"One folder per item, no nesting" is a PM-owned assumption, asserted not researched** (`01-scope-review.md` § Stage decision). Decision 1 in Architecture keeps single-membership a *policy* rather than a foreclosing shape specifically so this can change later without a rewrite — the next PRD touching folders should treat this as an open product question, not settled precedent.
- **`ADV-4` and `ADV-5` should be folded into the HTTP-endpoints follow-up, not left as standalone advisories.** `listFolders` returns live object references including `userId` (harmless today, becomes a DTO leak the moment an HTTP route serialises a folder record directly); `listItems(userId, null)` throws a `TypeError` instead of treating `null` as "no filter" (harmless internally, becomes an ungraceful 400 the moment a query-param parser passes `null` through). Both are cheap to fix but only matter once folders gain a transport surface — the next slice's Architecture stage should treat these as known input, not rediscover them.
- **Context-pack staleness has no owning stage, and this is now a repeat finding.** The EM flagged `.agentic/PROJECT_CONTEXT.md` as stale (still describes `addItem`/`listItems`/`softDeleteItem` as the whole surface, missing `bulkDeleteItems`, `digest.js`, `summary.js`, `emailAdapter.js`, `server.js`) — and noted the *same class* of staleness was flagged by the `email-digest` EM about `CURRENT_MVP_STATUS.md` and only partly fixed (`01-scope-review.md` § Flags for the Orchestrator). Two slices in a row have hit this. Recommend the Orchestrator assign context-pack maintenance as a standing Post-Launch task rather than waiting for a third EM to re-flag it.
- **The 5-vs-3 `listItems` call-site undercount is a process note for Scope Review's own sizing method**, not a defect: grepping `src/` alone missed `scripts/drill/`. Future scope-sizing passes that enumerate call sites should grep `scripts/` too, not just `src/`.
